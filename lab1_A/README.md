Окружение: Ubuntu 24.04.1 LTS под WSL, x86-64; g++ 13.3.0, GNU Binutils 2.42.

## Этап 1. Препроцессинг

```console
$ g++ -E simple.cpp -o simple.i
```

Флаг -E останавливает обработку после препроцессора. В simple.i сохраняется текст единицы трансляции после обработки директив препроцессора.

### 1. Сколько строк было в исходном файле и сколько стало в .i?

Исходный файл содержит 23 строки, результат препроцессинга 1073 строки. Подсчёт включает пустые строки и служебные строки препроцессора.

### 2. Где находится main, что находится над ней и почему так много строк?

main находится на 1068 строке. В начале simple.i находятся строки:

Непосредственно перед `main` находятся определения `global_counter`, `MAGIC`, `square`, `sum_of_squares` и `bump_counter` из исходной программы. Выше них находится содержимое `<cstdio>` и подключённых им заголовков: объявления функций ввода-вывода (включая `printf`), типы, пространства имён и using. Вложенные `#include` также раскрываются, в основном там объявления.

### 3. Где оказалась строка формата и что с ней сделал препроцессор?

Строка осталась внутри вызова printf в main, на строке 1071. Содержимое строкового литерал не изменилось: спецификаторы %d и последовательность \n сохранены. Препроцессор не форматирует строку и не заменяет MAGIC значением 42: MAGIC - это константа языка C++, а не макрос #define. Интерпретация escape-последовательностей происходит на последующих этапах трансляции, а подстановка чисел вместо %d уже при выполнении printf.

## Этап 2. Компиляция и оптимизации

```console
$ g++ -x c++-cpp-output -S -masm=intel -O0 simple.i -o simple_O0.s
$ g++ -x c++-cpp-output -S -masm=intel -O2 simple.i -o simple_O2.s
```

Флаг -S останавливает сборку на ассемблерном тексте, -masm=intel выбирает синтаксис Intel, -O0 отключает оптимизации этого уровня, -O2 включает набор оптимизаций. Флаг -x c++-cpp-output явно задаёт вход как уже обработанный препроцессором C++.

### 4. Сравнение размеров файлов с -O0 и -O2.

```console
$ wc -lc simple_O0.s simple_O2.s
 144 2497 simple_O0.s
  96 1666 simple_O2.s
 240 4163 total
```

Отношение размеров ассемблерных файлов: 2497 / 1666 = 1.5, то есть файл с -O2 примерно в 1.5 раза меньше.

### 5. Какие инструкции используются для умножения в square без оптимизации?

В C++ имя square(int) кодируется компилятором в _Z6squarei. Поэтому вместо буквальной метки square: нужно искать _Z6squarei:.

```console
_Z6squarei:
.LFB2:
    .cfi_startproc
    endbr64
    push rbp
    .cfi_def_cfa_offset 16
    .cfi_offset 6, -16
    mov rbp, rsp
    .cfi_def_cfa_register 6
    mov DWORD PTR -4[rbp], edi
    mov eax, DWORD PTR -4[rbp]
    imul eax, eax
    pop rbp
    .cfi_def_cfa 7, 8
    ret
    .cfi_endproc
.LFE2:
    .size _Z6squarei, .-_Z6squarei
```

Умножение выполняет инструкция imul eax, eax: число в eax умножается на само себя. Аргумент x приходит в edi, без оптимизации сохраняется в стек, а затем загружается в eax. Результат функции возвращается в eax.

### 6. Какие регистры передают аргументы sum_of_squares и почему?

Фрагмент main из simple_O0.s:

```asm
mov esi, 4
mov edi, 3
call _Z14sum_of_squaresii
mov DWORD PTR -4[rbp], eax
```

Первый аргумент a = 3 передаётся в edi, второй b = 4 - в esi. Это младшие 32 бита регистров rdi и rsi, поскольку аргументы имеют тип int. В Linux x86-64 применяется System V AMD64 ABI: первые шесть целочисленных аргументов передаются в rdi, rsi, rdx, rcx, r8 и r9 соответственно, с учётом размеров типов. Порядок команд mov не меняет соответствие аргументов регистрам. Результат типа int возвращается в eax.

### 7. Исчезла ли square при -O2 и что произошло при оптимизации?

В полученном файле отдельная функция square не исчезла:

```asm
_Z6squarei:
.LFB2:
    .cfi_startproc
    endbr64
    imul edi, edi
    mov eax, edi
    ret
    .cfi_endproc
.LFE2:
    .size _Z6squarei, .-_Z6squarei
```

При этом вызовы square внутри sum_of_squares заменены вычислениями:

```asm
_Z14sum_of_squaresii:
.LFB3:
    .cfi_startproc
    endbr64
    imul edi, edi
    imul esi, esi
    lea eax, [rdi+rsi]
    ret
    .cfi_endproc
.LFE3:
    .size _Z14sum_of_squaresii, .-_Z14sum_of_squaresii
```

Это встраивание (inlining): вместо call помещены операции тела функции. В main результат sum_of_squares(3, 4) вычислен во время компиляции:

```asm
mov esi, 25
```

В main больше нет вызовов sum_of_squares и bump_counter: вычисление 25 свёрнуто в константу, а увеличение счётчика встроено в main. Отдельные определения square и sum_of_squares сохранены, поскольку имеют внешнее связывание и могут вызываться из других единиц трансляции. Обычная компиляция без анализа всей программы не может считать их ненужными. Таким образом, предположение задания об исчезновении square не является обязательным результатом -O2: здесь исчезли вызовы, но осталось определение.

## Этап 3. Ассемблирование в объектный файл

```console
$ g++ -c simple_O0.s -o simple.o
```

На этом этапе ассемблируется результат предыдущего этапа без оптимизации, флаг -c запрещает компоновку

```console
$ nm simple.o
0000000000000044 T _Z12bump_counterv
0000000000000013 T _Z14sum_of_squaresii
0000000000000000 T _Z6squarei
0000000000000000 r _ZL5MAGIC
0000000000000000 B global_counter
000000000000005e T main
                 U printf
```

T обозначает символ кода, B - данные с нулевой инициализацией, U - пока не определённый внешний символ. Реализация printf находится в стандартной библиотеке, а не в simple.o.

### 8. Почему MAGIC относится к read-only data, а не data?

MAGIC объявлена как **const** int и в этом объектном файле размещена в .rodata, секции данных только для чтения, а не в изменяемой .data. 

### 9. Что показывает size и какие секции занимают больше всего места?

```console
$ size simple.o
   text    data     bss     dec     hex filename
    400       0       4     404     194 simple.o
```

В стандартном формате GNU size:

- text - код и учитываемые данные только для чтения, 400 байт;
- data - инициализированные изменяемые данные, 0 байт;
- bss  - область нулевой инициализации, 4 байта;
- dec  - сумма text + data + bss в десятичной записи, 404;
- hex  - та же сумма в шестнадцатеричной записи, 194.

Для детализации по секциям:

```console
$ size -A simple.o
simple.o  :
section              size   addr
.text                 172      0
.data                   0      0
.bss                    4      0
.rodata                44      0
.comment               46      0
.note.GNU-stack         0      0
.note.gnu.property     32      0
.eh_frame             152      0
Total                 450
```

Наибольшие секции - .text (172 байта, машинные инструкции функций) и .eh_frame (152 байта, метаданные для раскрутки стека). Для столь маленькой программы служебные метаданные сопоставимы по размеру с кодом. .rodata занимает 44 байта: MAGIC, строка формата и выравнивание. .bss содержит 4-байтовый global_counter, изначально равный нулю. Его нули не хранятся в файле как четыре обычных байта данных, место выделяется и обнуляется при загрузке. Поэтому .data пуста, а global_counter имеет тип B.

Колонка text в обычном выводе size не равна одной секции .text: здесь она включает .text (172), .rodata (44), .note.gnu.property (32) и .eh_frame (152), в сумме 400 байт. size -A дополнительно учитывает .comment (46), поэтому его Total равен 450, тогда как dec в обычном выводе равен 404. Ни 404, ни 450 не являются полным размером файла simple.o на диске: объектный ELF-файл также содержит заголовки, таблицы символов и релокации.

## Этап 4. Компоновка и запуск

```console
$ g++ simple.o -o simple
```

Компоновщик объединяет объектный файл со стартовым кодом и подключает необходимые библиотеки. Получается исполняемый файл.

### 10. Какой результат вывела программа?

```console
$ ./simple
Result: 25, Counter: 1, Magic: 42
```

`sum_of_squares(3, 4)` вычисляет `3 * 3 + 4 * 4 = 25`. `bump_counter` увеличивает `global_counter` с 0 до 1. `MAGIC` равна 42. Программа завершилась успешно, код возврата - 0.
